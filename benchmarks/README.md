# Benchmark publication

Source repositories: NuSTAR, NuExpansionHunter, NuTRF, NuMAFFT and NuVCFtools. Each maintains `benchmarks/published.json` on `main`; this directory is the initial validated snapshot. `scripts/benchmarks.py` defines the shared version-1 data contract. The renderer escapes text and links and computes ratios from measured values.

`Publish benchmark tables` fetches each main SHA, downloads that exact revision's data, validates all source records, builds the site and deploys it through GitHub Pages. A dispatch payload cannot select a repository, revision or executable. Concurrent publication runs are serialized and always read current main. Publication runs on repository dispatch, manual request and hourly fallback. It never executes benchmark programs.

The workflow uploads `benchmark-provenance` with the exact source revisions and published records. Automated runs do not commit generated HTML back to main. For local preview, run `python3 scripts/sync_benchmarks.py` then `python3 build.py`; without fetching, the build uses the checked-in snapshot. Run `python3 -m unittest discover -s tests -v` before changing the publisher.

Only benchmark rows, table headers, captions, benchmark notes and Performance Improvement cells are generated. Project descriptions, Validation cells, upstream activity dates and the rest of the page remain in `template.html`.

The Pages source is **GitHub Actions**. The private **BioCode Benchmark Publisher** GitHub App belongs to the organization and is installed only on this website repository. It has Actions write permission and mandatory Metadata read permission, with no Contents or Workflows write permission. Each source workflow creates a token restricted to this installation, triggers `benchmarks.yml` on `main`, and revokes the token at job completion. Hourly polling remains a fallback.

Each source repository uses Actions variable `BENCHMARK_APP_ID` and encrypted secret `BENCHMARK_APP_PRIVATE_KEY`. The organization administrator owns App management and key rotation. To rotate, generate a new App private key, replace the secret in each source repository, run each **Published benchmark** workflow, and verify a successful website deployment before deleting the previous App key. Never store private keys in source control, logs, issues or chat. No personal publishing token is required.

For maintainer handover, keep project-level review within each source repository and transfer publisher administration separately. No workflow depends on an individual maintainer's name. Review schema changes against all existing data files before deploying them. A successful notification means the website accepted the request; the deployment workflow is the authority for whether it went live.

A fetch, validation, build or deployment failure preserves the previous deployed website. Review the failed workflow before retrying; never relax the schema to accept incomplete results. Changes to timing scope, RSS scope, hardware or repetitions must also update captions/notes and pinned evidence. An index-construction row is separate from sample processing; do not combine its resources with sample measurements.

A project without reviewed results publishes only `schema_version: 1`, its registered `project` name and `status: "unpublished"`. The site displays that state without a numeric table. For the first measurement, replace the entire record with the measured format (see [NuSTAR.json](NuSTAR.json)). A measured record requires a pinned evidence link and at least one complete row with positive times and memory values. `memory_metric` defaults to `Peak RSS`; use `Peak RAM` when that is the metric reported by the source and describe the accounting scope in `rss_scope`. A missing file, empty measured table, or mixed state fails validation.
